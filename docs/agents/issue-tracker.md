# Issue tracker: GitHub

명세와 작업 티켓은 WinterFramework-org/winter-samples의
GitHub Issues에 기록한다. GitHub 작업은 gh CLI를 사용한다.

이번 최신화의 전체 계획은 https://github.com/WinterFramework-org/winter-samples/issues/1 이다.

## 작업 규칙
- 이슈를 읽을 때 본문, 라벨, 댓글을 함께 확인한다.
- 여러 줄 본문과 댓글은 파일로 작성하고 --body-file로 전달한다.
- 전체 목표와 하위 작업은 GitHub의 sub-issue 관계로 연결한다.
  해당 기능을 사용할 수 없으면 본문에 부모 이슈 링크를 기록한다.
- 작업 간 선행 조건은 native issue dependencies로 기록한다.
  해당 기능을 사용할 수 없으면 본문에 Blocked by 링크를 기록한다.
- 상태 라벨은 docs/agents/triage-labels.md의 매핑을 사용한다.
- 스킬에서 명세나 티켓 게시를 지시하면 GitHub 이슈로 등록한다.

## 이슈 작성
- 사용자가 확정한 요구사항과 양식을 우선한다. 이 저장소에서는
  아래 양식을 사용하고, 스킬별 기본 템플릿으로 다시 바꾸지 않는다.
- 제목에는 실제 변경할 내용을 쓴다. 공통 접두사나 부모 작업명을 붙이지 않는다.
- 본문은 `배경` → `변경할 내용` → `완료 조건` → `관련 이슈`로 구성한다.
- 배경은 현재 상태와 변경 이유를 설명한다. 기존 코드가 이해에 도움이 되면
  해당 설명에 커밋과 줄 번호를 고정한 GitHub 링크를 넣는다.
- 코드 참조는 `기능 설명 (파일명의 메서드)` 형태로 쓴다.
  링크 이름은 실제 파일명으로 하고, 메서드명과 역할은 주변 문장에 적는다.
  파일 전체를 설명할 때는 메서드명을 생략한다.
- 기준 버전은 `winter-framework v0.2.0`처럼 저장소 이름과 버전을 표시하고,
  해당 버전의 기준 커밋으로 직접 연결한다. 커밋 해시는 링크 주소에만 둔다.
- 핵심 프레임워크 연동 동작은 구현 근거가 필요한 설명에 같은 방식으로
  코드 링크를 넣는다. 다른 저장소의 파일은 주변 설명에 저장소 이름을 명시한다.
- 변경할 내용에는 기대 동작과 필수 제약을 명시한다.
  세부 파일·클래스·메서드 구성은 구현 과정에서 정한다.
- 완료 조건은 관찰 가능한 결과를 체크리스트로 쓴다.
  테스트 실행 결과와 확인 증거는 PR에 남긴다.
- 관련 이슈에는 실제 전체 계획·선행 작업 링크를 넣는다.
  등록 순서나 링크 교체 지시 같은 작성용 메모는 게시하지 않는다.
- 본문은 현재 요구사항을 유지하고, 진행 상황·발견한 제약·결정 이유는
  댓글에 기록한다. 요구사항이 바뀌면 본문과 변경 이유를 함께 갱신한다.

## 스킬 적용
- `to-spec`은 전체 요구사항·설계·검증 범위를 정리한다.
- `to-tickets`는 독립적으로 확인 가능한 작업과 선행 관계를 정리한다.
- 두 스킬의 내용 요구를 위 양식에 담는다. 별도 User Stories 목록이나
  기본 영문 항목을 추가하기 위해 합의한 본문을 반복하지 않는다.
- 이번 winter-samples 최신화에는 `github-issue-draft`를 적용하지 않는다.
- 용어집은 용어 정의를 기록한다. 구현 계획과 API 계약은 이슈에 기록한다.
